# 核验与写作铁律

这些规则是本刊可信度的全部来源。**任何一条与「多出点内容」冲突时，都是规则赢。**

## 一、来源与核验

1. **不信检索索引**。Google/Bing/arXiv 检索页的摘要、作者、单位一律不作数。每条进正文的论文必须
   取原文核：`python scripts/fetch_source.py <arXiv id | DOI | URL>`（arXiv Atom API / Crossref /
   页面转纯文本）；必要时读 PDF 致谢/脚注确认机构。**不要直接 curl arXiv abs 整页**——
   43k 字符 vs 2k，纯烧 token。
2. **作者与单位逐位核**。核不到单位写「待确认」。**绝不以人名、口音、合作网络猜单位或国别。**
3. **每个数字必须能追到一个 URL**。追不到的数字不写。
4. **一手优先**。论文 > 官方新闻稿 > 行业媒体转载。营销落地页、专利、供应商目录**不作为论文来源**。
5. **时间窗内**。窗口 = 上期日期之后至本期日期。窗外但高价值的可收，但必须标「（窗口外补记）+ 原始日期」。
6. **同行评审 vs 预印本**必须标明。预印本一律写「arXiv 预印本（YYYY-MM）、未同行评审」。

## 二、事实 / 前瞻 分离

7. **厂商宣称**的性能数字，写成「厂商宣称 …」，不得写成既成事实。
8. **分析师 / 市场规模 / 渗透率预测**（TrendForce、MarketsandMarkets、Omdia、Dell'Oro 等）
   **只能进第五节「⚠️ 前瞻 / 分析师数字（不作既成事实）」**，不得混入前四节。
9. **未发布产品**写成「预告 / 将出产品的信号，非已发货」，并注明揭晓日期。
10. 口径变化（例如渗透率从 47% 改为 53%）要**显式写出是哪家哪次更新**，不要静默替换。

## 三、去重与连续性

11. 起草前必读 `drafts/reported-index.md`。命中已报**标题 / arXiv id / DOI / URL** 的候选 = 不再重复报道；
    只有出现**实质进展**（同行评审接收、硬件实测、规格揭晓）时，才以一句话「进展更新」提及并注明原报期数。
12. 长期缺口要**连续计数**：「连续第 N 期仍缺」。缺口消失了也要显式说明补上了。
13. 「开放问题 / 下期」里挂的账，下一期必须逐条回应（补上了 / 仍缺 / 已放弃并说明原因）。

## 四、写作

14. **不凑数**。内容稀的一周就写薄的一期，并在「方法与局限」里如实说明本期短板。
15. 论文卡固定五段：**研究团队 / 技术介绍（含性能）/ 技术优势（先进性）/ 技术局限 / 来源**。
16. 正文中文；专业术语首次出现给「中文（English）」或「English 中文」对照，之后可只用一种。
    **写作语言是中文，文献来源只收英文**——两件事不要混（见 `SKILL.md` 覆盖面）。
    不用英文网络缩写作小标题（如 TL;DR），一律写成中文（「一句话总览」）。
    **抬头只留「主题」「时间窗」两行**，不写「方法」行、「说明」行。
17. 数字带单位，温度 `°C`、压降 `kPa`、功率 `kW`；相对量写清基准（「相对常规设计 −72.8%」）。
18. 不写形容词式评价（「革命性」「颠覆」）。先进性用**与现有方法的具体差别**说明。
19. 署名固定：`*—— Sage · 散热方案周报第 N 期（待核验稿）*`。

## 五、流程

20. **绝不直接推 `main`**。一律 `briefing/<日期>` 分支 + PR——PR 是审计留痕与部署闸门，不因自审通过而省略。
    **合并权限分两种情况**：
    - **未命中下列触发项** → 走第 25 条自审，**通过后 agent 自行合并**（`gh pr merge <N> --rebase --delete-branch`），
      并确认 Pages 部署成功、站点已更新。
    - **命中下列任一触发项** → **PR 保持 open、agent 不得合并**，在 PR 正文**开头**与回报里点名命中了哪几项，等维护者裁定：
      - **(a) 更正前期内容**——修改、补正或推翻任何已发布期次的陈述；
      - **(b) 撤回已发布数字**——收回或作废此前期次发布过的数字、日期、口径；
      - **(c) 窗口外补记**——本期收入任何标「窗口外补记」的条目；
      - **(d) 厂商宣称类数字**——正文任何位置出现以「厂商宣称 / 厂商口径 / 厂商标称」标注的数字。
    判断从严：**拿不准算不算命中，就算命中**——停下来等人的代价远小于把错的东西推上公网。
21. 调 `scripts/ingest_briefing.py` 必须带 `--no-push`。
22. 推分支前跑 `mkdocs build --strict`，构建不过不开 PR。
23. PR 正文必须列出**逐条来源**与**本期未核 / 待确认项**，方便人工只复核风险点。
24. **出稿流程问题不进周报**。网络被拦、脚本报错、token/限流、会话中断、云端/本地切换、检索漏检或把两条混成一条等
    **agent 自身的运行问题**，与读者无关——不写进「方法与局限」或正文任何位置。
    这类问题只写在 PR 正文末尾的「流程备注」里（不发布），由维护者归档。
25. **合并前必须自审，自审不是过场。** 顺序：① 把 `rules.md` 第 1–24 条对成稿逐条过一遍；
    ② 走 `TEMPLATE.md` 末尾的「常见反模式」自检表；③ **抽查跨期引用**——凡正文写「第 N 期已报」
    的地方，回仓库 `grep` 验证期号与当时的结论（**曾被某期判为「核验未通过」而排除的数字，不得在后续期次当作已报数据复用**）；
    ④ 核对本期声称的「连续第 N 期缺口」计数与上期是否衔接。
    **发现问题先改稿、重跑 `mkdocs build --strict`、追加提交，再谈合并**；改动要在回报里逐条说明改了什么、为什么。
    自审中若改出了第 20 条的任一触发项（例如为修正而动了前期内容），**按命中处理，停下来等人**。
